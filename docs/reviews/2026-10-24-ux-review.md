# 界面原型交互评审（2026-10-24）

> 评审对象：原型 v0.1（`prototype/` 与 `docs/prototype.md` 初版）。评审者：独立 agent（Opus，xhigh）。所有问题已在原型 v0.2 中处理，处理方式见文末。

## 1. 总评

视觉骨架和三栏分区站得住，但两件最关键的事没设计：**消息发到哪个上下文、签名时签的是什么**。@上下文静默跟随选中项、审批一键签名且全程看不到 head SHA、"需要你"在各入口不一致，导致核心流程在"决定 → 合并完成"这一段断开。

## 2. 问题清单

〔bug〕= 代码行为与规格或常识不符；〔设计〕= 交互设计问题。

### 阻断

**#1 审批是一键签名，签之前看不清签的是什么，历史里的按钮也不会失效**〔设计 + 规格〕

- 按钮文案即动作，点了直接弹生物识别；动作、目标、head SHA、diff 都不在卡片上，整个工作区没有显示 head SHA 的地方。
- 选中 Issue #4 时检视器出现不带目标的"签名批准 merge"（代码写死 `MAP i4→p9`）。
- 气泡是静态历史：新推送、已批、过期后旧按钮仍可点；多个待签 PR 时出现多个同名按钮。
- data-model §4.4 没有"签名前 head 就变了"（`pending → invalidated`）。
- 文案写死 Touch ID，Windows 应为 Windows Hello。
- 改法：新增"审批单"作为唯一签名处；所有入口改为"审阅并签名…"只打开审批单；审批单显示动作、仓库、PR、完整 head SHA、改动与策略命中、合并闸门、有效期；签名载荷用审批单上的 SHA；各入口绑定同一个审批并实时显示状态。

### 高

**#2 @上下文跟着检视器选中项走，容易把消息发进错误的交付单元**〔bug + 设计〕：默认就是 @#5；点引用 chip 会同时改发送目标；用户气泡不显示发往哪里；"回复「修」"会落到错误交付。改法：选中只驱动检视器；@ 改为可选择、可清除的按钮；检视器加"在对话中引用"；agent 气泡加"回复"；用户气泡显示 `@上下文 · 上限`；默认和每次发送后复位为"全项目"。

**#3 合并段缺 GitHub 审批闸门和"完成"反馈**〔设计〕：App 创建的 PR 必须由用户在 GitHub 上 approve，原型没有体现；签名后的过程完全不呈现。改法：检视器和审批单加闸门清单；GitHub 侧未满足时禁用签名；签名后依次显示排队、已合并、Issue 已关闭；完成项移入"最近完成"。

**#4 "需要你"各入口不一致**〔bug + 信息架构〕：顶栏计数随项目切换；PR #1 的待办在左栏不可见；同一概念五种说法；检视器只能放一条。改法：所有表面由 open 的上报项投影，顶栏为全局计数，tab 带徽标，左栏和地图带"需要你"标记，气泡带类型标签，检视器列出全部；统一术语。

**#5 档位选择器没有表达"上限"**〔bug + 设计〕：默认值与项目默认不符；发送后不复位；无"上限"字样；@已有交付时的语义未定义；文字与选择器冲突未定义；升档无界面；None 档回复错误。改法：标签"上限"、默认项目默认值、发送后复位、悬停说明、显示交付上限并提示改动影响、检视器显示"上限 · 实际"、新增"需要升档"上报。

**#6 空项目用空态替换了整个对话**〔bug + 设计〕：改为在对话视图内显示空态卡，输入区始终可用；地图和工作树各自有空态。

**#7 工作页没有确定性的"停"**〔设计〕：检视器加暂停 / 继续、重试失败节点、放弃交付（带确认）。

**#8 状态几乎只靠颜色点，"自愈中"和"等你"难以区分**〔设计 / 可访问性〕：需要你用带"!"的文字药丸；静默处理用中性色；橙色只留给失败且无人处理。

### 中

- **#9 离开后回来难以知道发生了什么**：加"上次查看"分隔线与离开期间摘要；连续事件折叠；事件行可点。
- **#10 跨项目、跨页面的状态泄漏和丢失**：草稿、上下文、上限、选中项、视图按项目保存；设置用浮层打开不卸载工作区。
- **#11 地图高亮和关联链跨过了交付单元**：按交付单元计算高亮与关联链，refs 单独一行。
- **#12 设备角色在界面上没有体现**：顶栏显示角色；只读设备禁用输入；非审批设备的签名按钮给出说明。
- **#13 连接、发送、外部变化、错误状态缺失**：合并连接指示；断线横幅、禁用签名、消息待发送；外部变化以事件行呈现。
- **#14 长内容和规模**：排序、折叠、标题悬停全文、地图过滤与自动布局。
- **#15 "+ 新建工作树"没有流程**：改为"从分支开始任务…"；点 main 显示基线信息。
- **#16 进度在对话和检视器里表达不一致**：计划卡标"实时"；检视器只列当前阶段的图；跳过的阶段画斜纹；明确对话与检视器的分工。
- **#17 设置页"项目设置"是死链，保存影响没有提示**：加"项目"分组；全局值标注被覆盖情况；保存提示生效时机；未保存拦截。
- **#18 手机端缺少"需要你"汇总，上限与上下文规则未定义**：加"需要你 · n"；固定项目默认上限；区分可在手机答复与需桌面签名的事项；多行输入。
- **#19 键盘与焦点**：真实的 ⌘↵ / Ctrl+Enter 发送且尊重输入法；可见焦点框；可聚焦的表格行；`aria-current` / `aria-selected`；档位选择器方向键漫游；跳转链接。
- **#20 agent 气泡边框颜色太弱，且与状态色、档位色重叠**：种类文字移入气泡左上角；边框 2px；agent 改用紫 / 青 / 灰；档位徽标去色；"需要你"独立表达。

### 低

- **#21 设置页"档位 × 三类模型"表与架构矛盾**：先定义"查询类消息由谁回答"，再改表。
- **#22 零散实现 bug**：CI 文字误用状态色；未知 agent 种类回退为大脑色；长对话把输入区推出视口且不自动滚动；设置页大脑卡橙框像警告；对话头部写死项目名。

## 3. 做得好的地方

1. 检视器把交付阶段、图和后台守护处置放在一起，"静默但可审计"在界面上成立。
2. 配置与工作分离干净。
3. 孤儿 PR 的橙色虚线配合"创建 Issue 并关联"，把规格规则变得可见。
4. 工作树表的"写权"列对应锁机制。
5. 手机端克制。

## 4. 取舍与处理

| 取舍 | 采用 |
| --- | --- |
| @上下文跟随选中还是显式指定 | 显式指定，配合"在对话中引用"和"回复" |
| 单一项目对话流在 Ultimate 下会混杂 | 保留单流（D-10），靠事件折叠、回复绑定交付缓解；按上下文过滤列为后续 |
| D-12 与状态色冲突 | 保留"边框区分 agent 种类"，agent 改用紫 / 青 / 灰，档位徽标去色，"需要你"用独立药丸 |
| 手机端能否做不需要签名的决定 | 文字答复、补规格、二选一可以；升档（增加花费）与签名只在桌面 |
| 单个交付的升档算控制还是配置 | 控制：在上报卡上一次完成；全局模板与上限只在设置页 |
| 工作页是否放确定性控制按钮；签名是否要求 GitHub 侧闸门先满足 | 都是 |
